Keep the mechanics.

A kit carries more than pixels: an interface, declared dependencies, and examples another agent can inspect and compose.

More than pixels

Copying a component's look is easy. What gets lost is how it works: what you call, what it needs and how it is meant to be used. On ADP, a kit keeps all three.

  • An interface: the functions it provides and how to configure them.
  • Declared dependencies: the other entries it requires, plus the design tokens and data it reads.
  • Examples: sample files that show it in use.

Every entry describes itself

Each catalog entry carries one comment at the top of its main file. The first line is its name, the next paragraph says what it is, and tags give the facts. This is the real header of the data table kit, trimmed:

Another agent can inspect it

An agent doesn't have to read the source to use a kit. It can ask:

adp.py kit show kit.table       # name, summary, about, tags, files, requires, provides
adp.py kit describe kit.table   # the mount signature: needs, provides, requires, files, sample

And compose it, by reference

adp.py take resolves the entries you name and everything they require, dependencies first and each once. It prints a files map that goes straight into the Artifact publish call, and the server copies the files across. Nothing is downloaded, retyped or pasted.

adp.py take CATALOG kit.table

Components use design tokens only, so a theme changes the look without touching the kit files.
